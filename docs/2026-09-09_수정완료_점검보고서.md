### H-1. 정산 보류 기간 실제 적용

**문제** 화면과 캘린더는 "영업일 5일 후 정산" 이라 안내하는데 `getSettlementSummary` 는 결제 시각을 보지 않아 **오늘 결제된 후원도 즉시 전액 요청 가능**했다. 환불 가능 기간 안에 지급되면 원장이 음수가 된다.

**수정**
- `computeHoldingAmount(creatorId, client, now)` 신설.
  - 최근 40일(`HOLDING_LOOKBACK_DAYS`) 후원만 훑어 `settlementDateFor(paidAt) > 오늘` 인 건을 고른다. 5영업일은 연휴를 감안해도 40일 안에 반드시 도래하므로 그 밖은 계산에서 빼도 결과가 같다.
  - 그 후원들에 달린 **원장 분개 전부**(총액·수수료·환불·수수료 환입)를 순액으로 합산한다. 환불로 순액이 음수면 0 으로 본다.
  - `IN` 절은 1,000개씩 끊어 파라미터 폭주를 막는다.
- `SettlementSummary` 에 `holding` 필드 추가. `available = balance - pending - holding`.
- `createSettlementRequest` 의 초과 오류 문구에 보류 금액을 함께 안내.
- 화면
  - `/studio/settlement` 타일을 5칸으로 재구성: 월 후원 합계 · **확정 잔액** · **정산 예정** · 정산 보류금 · 정산 완료금. `grid-cols-2 sm:grid-cols-3 lg:grid-cols-5` 로 모바일 대응.
  - 정산 요청 탭에 "확정 잔액(요청 가능)" / "정산 예정(요청 불가)" 을 분리 표기. 잔액 0원·최소금액 미달 안내문도 보류 금액을 함께 설명하도록 고쳤다.
  - `/admin/settlements` 요약 표와 `/admin/creators/[id]` 타일에도 "정산 예정" 을 노출.

**파일** `src/server/services/settlement.ts`, `src/app/studio/settlement/page.tsx`, `src/app/admin/settlements/page.tsx`, `src/app/admin/creators/[id]/page.tsx`

**영향 없음 확인** `assertPayable` 은 이미 승인된 건을 지급 직전에 검증하는 경로라 `balance` 기준을 그대로 둔다. 요청 시점에 이미 보류 검사를 통과했으므로 보류를 다시 빼면 정상 지급이 막힌다.

### H-4. TTS 설정 이중 소유권 충돌 해결

**문제** 관리자 폼이 `voice` 를 `ko-KR-Standard-A~D` 로 강제하고 `provider` 를 무시한 채 저장해, 크리에이터가 고른 브라우저 음성이나 CLOVA 화자(`nara` 등)가 **저장 버튼 한 번에 존재하지 않는 값으로 덮어써졌다.**

**수정**
- `updateCreatorTtsSetting` 에서 `voice` · `speed` 를 **제거**. 관리자는 `enabled / readAmount / readName / volume / minAmount / maxChars` 만 다룬다. upsert 의 `create` 도 `voice/speed/provider` 를 스키마 기본값에 맡긴다.
- 감사로그 before/after 도 관리자가 실제로 바꾸는 값 기준으로 교체.
- `/admin/tts` 화면
  - 음성 선택 상자·속도 입력 삭제 → **읽기 전용 안내줄**("제공사 / 음성 / 속도")로 대체.
  - 페이지 설명·섹션 설명 문구를 소유권 경계에 맞게 갱신("음성·속도·제공사는 크리에이터가 오버레이 설정에서 직접 고릅니다").
  - 입력 그리드 5열 → 3열.

**파일** `src/app/actions/admin/broadcast.ts`, `src/app/admin/tts/page.tsx`

### H-6. 이체파일 제외 건 안내

**문제** `buildPayoutRows` 는 미인증 계좌·잔액 부족 건을 `logger.warn` 만 남기고 건너뛰었다. 관리자는 "선택 5건 → 파일 3행" 을 파일명 끝 숫자로만 알 수 있었고, 재발급 경고는 `X-Payout-Reissued` 응답 헤더라 브라우저 다운로드에서는 아무도 보지 못했다.

**수정**
- `buildPayoutBatch(requestIds)` 신설 → `{ rows, excluded }` 반환.
  - 제외 사유를 구분해 담는다: 계좌 미등록 / 실명확인 미완료 / `assertPayable` 이 돌려준 사유(잔액 부족 등) / 승인 상태가 아니거나 존재하지 않는 요청.
  - 기존 `buildPayoutRows` 는 `buildPayoutBatch(...).rows` 를 돌려주는 얇은 래퍼로 남겨 **기존 테스트 2개(`settlement-payout.test.ts`, `settlement-process.test.ts`)의 시그니처를 깨지 않았다.**
- `/api/admin/settlements/payout` 에 **`?preview=1` 확인 단계** 추가.
  - JSON 으로 `selected / included / excluded / totalAmount / reissue` 반환.
  - **상태를 바꾸지 않는다** — 배치번호를 발급하지 않으므로 여러 번 눌러도 발급 이력이 더럽혀지지 않는다.
  - 계좌번호·예금주 원문은 담지 않는다(그 값은 CSV 다운로드 전용).
  - 실제 다운로드 시 감사로그 `after` 에도 `excluded` 를 남긴다.
- UI: [지급대행 파일 받기]가 곧바로 다운로드하지 않고 미리보기를 불러온다. 확인 패널에서
  - "선택 5건 중 3건 이체 · 2건 제외" + 제외 건별 사유 목록
  - 재발급 건은 붉게 + 이전 배치번호 + 이중이체 경고
  - [확인했습니다 · 파일 받기] / [취소]
  - 선택이 바뀌면 미리보기는 자동 무효(effect 없이 `selectionKey` 비교로 처리).

## 5. 시뮬레이션 점검 (코드 레벨 검증)

실행 DB 를 건드리지 않고 호출 경로를 따라가며 확인한 결과다. (`npm test` 는 CLAUDE.md 지침에 따라 실행하지 않았다 — DB 를 비운다)

### 5.1 정산 보류(H-1) 시나리오

| 상황 | 기대 | 코드 경로 |
|---|---|---|
| 오늘 3,000원 결제 | `holding = 2,550`(수수료 차감 후 순액), `available = 0` → 요청 불가 | `computeHoldingAmount` 가 `settlementDateFor(오늘) > 오늘` 로 판정 → 해당 donation 의 원장 3분개 합계를 보류 |
| 6영업일 전 결제 | `holding = 0`, 전액 요청 가능 | 정산일이 이미 지나 immature 목록에서 빠진다 |
| 보류 중인 후원이 환불됨 | 보류 순액이 줄어들고, 환불이 커서 음수가 되면 `0` | 같은 donationId 의 `REFUND`·`REFUND_FEE_RETURN` 분개까지 합산 후 `holding > 0n ? holding : 0n` |
| 41일 전 결제 | 조회 범위 밖 → 보류 0 | 5영업일은 최대 연휴에도 40일을 넘지 않는다 |
| 트랜잭션 안 호출(정산 요청) | 잠금 안 스냅샷 사용 | `getSettlementSummary(creatorId, tx)` → `computeHoldingAmount(creatorId, tx)` 로 `client` 전달. `SummaryClient` 에 `donation` 추가 |
| 이미 승인된 건 지급 | 보류와 무관하게 지급 진행 | `assertPayable` 은 `balance` 기준 유지(요청 시점에 이미 보류 검사를 통과했다) |

### 5.2 심사 반려(H-5 · M-4 · M-7) 시나리오

1. 관리자가 상태를 REJECTED 로 고르고 사유를 비우면 → `'반려·정지는 사유를 입력해야 합니다'` 로 거절(저장 안 됨).
2. 사유를 넣고 제출 → `rejectReason` 저장 → APPROVED 였다면 세션 폐기 + 오버레이 연결 종료 → MO 번호 회수 → 알림 `"…심사 상태가 '반려' 로 변경되었습니다. 사유: …"`.
3. 크리에이터가 `/studio` 접속 → 레이아웃 게이트가 `rejectReason` 을 읽어 붉은 박스로 표시.
4. 나중에 APPROVED 로 되돌리면 → `rejectReason: null` 로 지워지고 MO 번호 자동 재발급.

### 5.3 이체파일(H-6) 시나리오

- 승인 5건 선택(그중 1건은 계좌 미인증, 1건은 다른 건이 잔액을 먼저 소진) → [지급대행 파일 받기] → `?preview=1` 응답: `included 3 / excluded 2` + 사유 2줄. **이 시점에 배치번호는 발급되지 않는다.**
- [확인했습니다 · 파일 받기] → 실제 GET → `markPayoutFileIssued` 로 배치 확정 → CSV 3행 + 감사로그에 `excluded` 2건 기록.
- 선택을 바꾸면 `selectionKey` 불일치로 미리보기 패널이 자동으로 사라진다(오래된 미리보기로 파일을 받는 사고 방지).

### 5.4 단건 정산 처리(H-3) 동시성

- 관리자 A 가 [승인], 관리자 B 가 거의 동시에 [반려] → 둘 다 `before.status = REQUESTED` 를 읽지만 `updateMany({ where: { status: 'REQUESTED' } })` 는 한쪽만 `count = 1`. 진 쪽은 `'상태가 이미 변경되었습니다…'`.
- 일괄 처리도 같은 규칙이 적용되어 "건너뜀 N건" 목록에 들어간다.

### 5.5 TTS 소유권(H-4)

- 크리에이터가 `provider=naver, voice=nara` 저장 → 관리자가 `/admin/tts` 에서 최소 후원금만 바꿔 저장 → **`voice`·`speed`·`provider` 는 DB 값 그대로**(update 데이터에 포함되지 않음). 화면에는 "제공사 네이버 클로바 Voice · 음성 nara · 속도 100%" 가 읽기 전용으로 남는다.
