## 0. 공통 구조 요약

### PaymentAdapter 인터페이스 (`src/server/adapters/payment/index.ts:93-125`)

```ts
export interface PaymentAdapter {
  info(): AdapterInfo;
  createRegistrationSession(input: { donorRef; returnUrl; notifyUrl; method? }): Promise<...>;
  completeRegistration(payload: Record<string, unknown>): Promise<...>;
  requestPinLink(donationId, amount, phone, method?): Promise<...>;
  approve(req: ApproveRequest): Promise<...>;
  inquire(orderNo): Promise<...>;
  cancel(input: { orderNo; providerTid; amount; reason? }): Promise<...>;
  revokeBillKey(billKey): Promise<...>;
}
```

### 결제 흐름 (end-to-end)

1. **등록**: `donor-registration.ts:161-168` → `adapter.createRegistrationSession()` → 결제창 리다이렉트 → `r/[token]/complete/page.tsx:135-139` → `adapter.completeRegistration()` → 빌키 암호화 저장(227)
2. **결제**: MO 수신 → `donation-flow.ts:783-788` `adapter.requestPinLink()` → PIN 링크 MT → `/api/webhooks/pin-callback` → `pin-authorization.ts:177` `executePayment()` → `adapter.approve()` → 실패 시 `adapter.inquire()`
3. **환불**: `refund.ts:120` `adapter.cancel()`, 불확실 시 `adapter.inquire()`
4. **해지**: `donor-registration.ts:279-281` `adapter.revokeBillKey()`

### 구조적 차단 (전 결제수단 공통)

**PIN 없는 결제수단이 결제에 도달하지 못함.**
`donation-flow.ts:793-805` — `requestPinLink`가 `ok:false`를 반환하면 곧바로 `PAYMENT_FAILED`로 확정. `PIN_NOT_SUPPORTED`를 처리하는 분기가 서비스/앱 계층에 단 하나도 없음(grep 결과 0건). 카드 빌키 방식(코엠·카카오)은 현재 구조에서 `approve`에 절대 도달하지 못한다.

**현재 `.env` 상태**: `PAYMENT_PROVIDER="mock"`, `SAFE_MODE="true"` → provider를 변경해도 mock으로 대체됨(`index.ts:276-279`). 4개 결제수단 모두 키가 비어 있어 지금 당장 실결제 불가.

### 인증 방식

- 서버 API 서명: `SHA256(mercntId + authNo + reqDay + reqTime + hashKey)` (96-104). approve/inquire/cancel에서는 `authNo` 자리에 `orderNo`를(383-389), revoke에서는 `billKey`를(511-517) 사용 — 규격 확인 전 추정.
- 결제창 해시: `SHA256(mercntId + ordNo + trDay + trTime + 평문금액 + callbackUrl호스트 + hashKey)` (111-123)
- 암호화: AES-256-ECB / PKCS#7 / Base64, 키 32바이트 강제 (135-143)
- HTTP: `Content-Type: application/json` POST, 인증 헤더 없음 (본문 signature만)

### 환경변수

필수: `HECTO_MID`, `HECTO_HASH_KEY`, `HECTO_AES_KEY`, `HECTO_CALLBACK_URL` (`hecto.ts:58-65`)

**.env 불일치 문제**: `.env`에는 `HECTO_API_BASE`, `HECTO_RETURN_URL`, `HECTO_NOTI_URL`이 있으나 코드는 이 세 변수를 **읽지 않음**(grep: src 내 사용처 0건). 코드가 읽는 `HECTO_AUTH_UI_BASE`/`HECTO_AUTH_API_BASE`/`HECTO_CALLBACK_URL`은 `.env`에 없음. `.env.example:52-56`은 새 이름을 쓰지만 `HECTO_CALLBACK_URL="${APP_BASE_URL}/api/payments/hecto/return"`으로 **존재하지 않는 라우트**를 가리킴.

### 웹훅/콜백

- 등록 복귀 `r/[token]/complete/page.tsx:138`가 `{tid, bankCode, bankName, account}`만 넘기므로 `completeRegistration`이 항상 `NO_AUTH_NO`로 실패함. **헥토 빌키 발급이 지금 코드로는 절대 완료되지 않는다.**
- PIN 콜백 `/api/webhooks/pin-callback`은 존재하지만 검증이 자체 규격(`X-Pin-Signature`/`X-Pin-Secret`, 55-99)이고 헥토 규격이 아님. 주석(23) "TODO: 실연동 시 결제사 서명으로 교체".

### 테스트 커버리지

`tests/adapters.test.ts:129-215`: 서명 재료 순서, 결제창 해시, callbackHost, KST 날짜, AES 왕복/키 길이, SPEC 경로 분리, 미설정 시 `AdapterNotConfiguredError`. 실제 요청 본문/필드명/응답 파싱 테스트 없음.

### 코드 내부 결함 (규격과 무관)

- `approve`의 `partner_user_id: req.buyerName ?? 'donor'` (278) — 등록 시 `partner_user_id: donorRef`(=registration.id, 164)와 다름. 카카오 정기결제는 동일해야 함 → 승인 거절 가능성.

- `method: 'CARD'` 고정 (235) — 계좌 연결이어도 CARD로 저장.

## 6. 우선순위별 액션 아이템

### P0 — 구조적 차단 (어느 결제사를 쓰든 필요)

**1. PIN 없는 결제수단 승인 분기 추가** (`donation-flow.ts`)
`requestPinLink`에서 `ok:false` + `code === 'PIN_NOT_SUPPORTED'`일 때 (또는 `token.method === 'CARD'`이고 provider가 koem/kakao일 때) `executePayment()`로 직접 가는 경로 설계. CLAUDE.md 규칙 7(DIRECT_TRIGGER는 서면승인 필요)과의 정합성 검토 필수.

**2. 운영 부팅 점검 provider별 분리** (`env.ts:479-486`)
`provider !== 'mock'`이면 무조건 헥토 키를 요구하는 로직 → provider별 필수 키 검사로 교체. `PAYMENT_PROVIDER=koem`으로 기동 시 헥토 키 없어도 정상 기동되어야 함.

**3. 등록 복귀 라우트 정비** (`r/[token]/complete/page.tsx`)
`{tid, bankCode, bankName, account}`만 넘기는 현재 payload를 provider별로 확장 (헥토 `authNo`, 카카오 `pg_token`) 하거나 `/api/payments/{provider}/return` 라우트 신설. `.env.example`의 `HECTO_CALLBACK_URL`이 가리키는 `/api/payments/hecto/return`도 실제 구현 필요.

---

### P1 — 헥토 (계약 진행 중, 가장 가까운 실결제 후보)

**4. 연동규격서 수령 후 SPEC 대조**
`HECTO_SPEC` 경로 4종, 필드명, 서명 재료(approve/inquire/cancel의 `authNo` 자리, revoke의 `reqTp`) 대조.

**5. `requestPinLink` 실구현** (`hecto.ts:331-357`)
`/v3/APIPayAuth.do` 실제 경로 확인 후 mock 코드 교체. `pin-callback/route.ts` 검증 로직을 헥토 서명 규격으로 교체.

**6. `.env` 변수명 정리**
`HECTO_API_BASE`/`HECTO_RETURN_URL`/`HECTO_NOTI_URL` 제거(코드 미사용), `HECTO_AUTH_UI_BASE`/`HECTO_AUTH_API_BASE`/`HECTO_CALLBACK_URL` 추가.

**7. 헥토 fetch 스텁 테스트 추가**
온기·코엠처럼 요청 본문, 필드명, 응답 파싱 테스트.

---

### P1 — 코엠 (등록 경로 이미 연결됨)

**8. 키 주입 및 IP 화이트리스트 등록**
`KOEM_MID`/`KOEM_API_KEY`/`KOEM_API_BASE` 설정, 서버 공인 IP를 코엠 측에 등록.

**9. inquire 구현 (선택)**
코엠 규격서에 조회 API가 없다면 타임아웃 건 전부 수동 대사 큐 처리(`donation-flow.ts:1135-1137, 1149-1159`). 조회 API가 없는지 재확인 후 결정.

**10. PCI-DSS 범위 확인**
카드번호 서버 경유(`card-registration.ts:14-17`) — 계약·인증 범위 검토.

---

### P2 — 카카오

**11. 공개 문서 대조 후 경로 재검증**
`subscription/register`→`payment/ready`, `completeRegistration`→`payment/approve` 분리 여부 확인. `subscription/sid` → `manage/subscription/inactive` 여부 확인.

**12. 내부 결함 수정**
- `partner_user_id`: 등록(`donorRef`)과 승인(`req.buyerName`)을 동일 값으로 통일
- `inquire`: `tid: orderNo` → `paymentTransaction.providerTid` 사용
- 등록 주문번호 저장 (`KAKAO-REG-...` → `paymentRegistration.providerRef` 등)
- `method: 'CARD'` 고정 → 실제 method 저장

**13. 환경변수 및 문서 정비**
`.env.example`에 `KAKAO_SECRET_KEY`, `KAKAO_CID` 추가. provider 주석에 `kakao` 추가.

### P2 — 온기

**14. API 경로 수령 후 SPEC 채우기**
`paymentCreatePath`, `paymentInquirePath`, `paymentCancelPath` 3개.

**15. 노티 수신 라우트 신설**
`/api/webhooks/ongi` (`verifyOngiWebhook` 활용, WebhookLog 기록).

**16. 결제 모델 설계 결정**
온기의 "건별 결제 URL" 방식을 현재의 빌키 모델(후원자 등록 → MO → 승인)에 어떻게 매핑할지 결정. 현재 `completeRegistration`이 무조건 실패하므로 후원자가 `UNREGISTERED`로 끝남.
