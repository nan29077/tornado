# 게임 오버레이 전체 점검 보고서

점검일: 2026-09-01
점검 방식: 소스 전량 재열람 + 실제 구동 확인(브라우저) + DB 직접 조회
점검 대상: 이번에 추가한 게임 오버레이 전체 (파일 22개, DB 표 4개)

---

## 0. 총평

**동작은 정상입니다.** 로그인 → 게임 띄우기 → 돌리기 → 결과 확정 → 내리기까지 실제 브라우저로 끝까지 돌려 확인했고, 결과가 DB에 제대로 남는 것까지 봤습니다. 지시하신 세 가지(크레딧류 제외 / 크리에이터에게 맞는 게임 / 토네이도 디자인·운영 UX)는 코드로 검증했습니다.

다만 **점검에서 결함 2건과 개선점 3건**이 나왔습니다. 서비스가 멈추는 종류는 아니지만, 하나는 제가 지난 보고에서 설명한 것과 실제 코드가 어긋나 있어 바로잡아 말씀드립니다.

## 2. 구현 인벤토리

**DB 4개 표** — `game` / `game_round` / `game_participant` / `game_winner`
정산·결제 표와 외래키로 연결하지 않음. 참여자 중복은 `(round_id, entry_key)` 유니크 제약으로 DB 레벨에서 차단.

**서버 서비스 6개**

| 파일 | 역할 |
|---|---|
| `game-catalog.ts` | 게임 8종 정의·검증·정규화 (클라이언트 공용, 서버 모듈 미참조) |
| `game-result.ts` | 추첨 순수 로직 (DB 무의존, CSPRNG 전용) |
| `games.ts` | 회차 생명주기 · 참여 · 후원 연동 |
| `game-state.ts` | 상태 스냅샷 (공개용/크리에이터용 분리) |
| `game-bus.ts` | 실시간 버스 (Redis Pub/Sub, 참여 폭주 시 0.7초 묶음 발행) |
| `game-stream.ts` | SSE 공용 구현 (버스 + 2초 주기 DB 재확인 이중 경로) |

**라우트 9개** — 스튜디오 5개(목록/생성, 수정/삭제, 진행 조작, 보상 체크, SSE), 공개 4개(참여 API, 참여 페이지, 게임 오버레이, 팝아웃 컨트롤)

**화면 4개** — 스튜디오 게임 탭, 게임 폼, 방송 오버레이(8종 렌더링), 시청자 참여 페이지

## 4. 점검에서 나온 문제

### 결함 1 (중) — 게임 오버레이 SSE 가 동시 연결 상한에 등록되지 않음

후원 알림 스트림은 `registerOverlayConnection()` 으로 크리에이터당 동시 연결을 세고 상한을 넘으면 오래된 연결을 끊습니다. **게임 스트림에는 이 호출이 없습니다.**

그래서:

1. 게임 오버레이 연결은 **상한이 없습니다.** 오버레이 토큰이 유출되면 후원 쪽은 막히는데 게임 쪽은 무제한으로 붙습니다.
2. 스튜디오 [현재 연결] 숫자에 **게임 소스가 잡히지 않습니다.** 크리에이터가 게임 소스를 OBS에 등록해도 0으로 보입니다.
3. 제가 지난 보고에서 "게임 소스가 하나 더 붙으니 상한을 3 → 6으로 올렸다"고 말씀드렸는데, **등록을 안 하므로 그 근거가 성립하지 않습니다.** 결과적으로 후원 소스 상한만 느슨해졌습니다. 이 부분은 제 설명이 틀렸습니다.

조치: 게임 스트림에도 등록을 붙이면 세 가지가 한 번에 해결됩니다. 몇 줄이면 됩니다.

### 결함 2 (중) — 참여 QR 이 로컬 주소를 가리킴

참여 링크를 `APP_BASE_URL` 기준으로 만듭니다(현재 `http://localhost:3025`). 그래서 **방송 화면 QR 을 휴대폰으로 찍으면 접속되지 않습니다.** 시청자 참여를 실제로 시험하려면 `.env` 의 `APP_BASE_URL` 을 외부에서 닿는 주소(터널 주소 또는 실서비스 도메인)로 바꿔야 합니다.

운영에서는 도메인이 들어가므로 정상 동작하지만, **지금 상태로는 참여 흐름을 휴대폰으로 시험할 수 없습니다.**

### 개선점 3 (하) — 마감 취소 후 자동 마감 시각이 복구되지 않음

[참여 마감] 시 `closesAt` 을 비우는데, [마감 취소]로 되돌릴 때 다시 채우지 않습니다. 그 회차는 이후 자동 마감이 걸리지 않고 직접 마감해야 합니다. 데이터가 깨지지는 않습니다.

### 개선점 4 (하) — 사다리 [번호별 시작]이 회차당 한 번뿐

첫 클릭에서 결과가 확정(RESULT)되므로 버튼이 사라집니다. 문구는 "번호를 골라 한 줄씩 따라갈 수도 있습니다"로 여러 번 가능한 것처럼 읽힙니다. 결과 목록에는 전원의 도착지가 함께 나오므로 기능상 손해는 없지만, **문구와 동작이 어긋납니다.**

### 개선점 5 (하) — 쓰이지 않는 내보내기 2개

`game-catalog.ts` 의 `ROUND_STATUSES`, `nextAction()` 이 어디서도 호출되지 않습니다. 버튼 로직을 컴포넌트 안에 직접 쓰면서 남았습니다.

## 5. 참고 — 부하 특성

상태 스냅샷을 **연결당 2초마다** 다시 만듭니다(참여자 집계·후원 합산 포함). 이 스트림을 구독하는 것은 **방송 오버레이와 크리에이터 화면뿐**이고 시청자는 구독하지 않으므로, 시청자가 늘어도 이 비용은 늘지 않습니다. 연결 3개 기준 초당 약 1.5회 질의입니다. 크리에이터가 많아지면 스냅샷 캐시를 고려할 지점입니다.

시청자 쪽 부하는 참여 API 한 번뿐이고, IP 분당 30건 제한 + 회차 유니크 제약으로 막습니다. **다만 수천 명 동시 참여 부하 시험은 아직 하지 않았습니다.**

## 6. 아직 하지 않은 것

- **실제 OBS·PRISM 브라우저 소스로 띄워보기** — 스튜디오 미리보기(같은 렌더링 경로)로만 확인했습니다
- 휴대폰 실기기 참여 (결함 2 때문)
- 동시 참여 부하 시험
- 관리자(`/admin`) 쪽 게임 관리 화면 (이번 범위 밖)
- 캐릭터 신규 에셋 (기존 5종 재배치로 대체)

## 7. 권장 조치 순서

1. **결함 1** 게임 스트림 연결 등록 — 몇 줄, 위험 없음
2. **결함 2** `.env` 의 `APP_BASE_URL` 을 외부 접속 주소로 (설정 변경, 코드 수정 아님)
3. **개선점 3·4·5** — 자잘한 정리
4. OBS 실등록 확인 → 휴대폰 참여 확인 → 소규모 실방송 시험

1·3·4·5는 제가 바로 고칠 수 있습니다. 지시 주시면 처리하겠습니다.
