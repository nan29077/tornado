## 1. 총평

**기반 설계는 이 규모의 프로젝트에서 보기 드물게 단단합니다.** 확인한 것만 적으면 이렇습니다.

- 중복 결제 4중 방어가 문서만이 아니라 **마이그레이션 SQL 에 실제로 존재**합니다 (`mo_inbound_message_provider_message_id_key`, `idempotency_key_scope_key_key`, `secure_link.usedAt` 조건부 소비, `payment_transaction_approved_uniq` 부분 유니크). 부수 제약까지 합치면 4중 이상입니다.
- 정산 원장 append-only 트리거가 실동작하고 테스트도 있습니다.
- 타임아웃 시 `inquire()` 로 확정하고, 불확실하면 단정하지 않고 `UNKNOWN` 으로 남겨 관리자 큐에 올리는 흐름이 코드 그대로입니다.
- AES-256-GCM 의 IV 를 매번 새로 뽑고 authTag 를 검증합니다. 추첨은 `Math.random` 이 아니라 `node:crypto` 의 `randomInt` 입니다. 토큰 비교는 전부 `timingSafeEqual` 입니다.
- 스튜디오 서버 액션 22개 전부가 `requireCreator()` 를 거치고 `creatorId` 를 where 절에 넣습니다. **테넌트 격리(IDOR)는 studio 영역에서 한 건도 발견되지 않았습니다.**
- 비밀번호 재설정 흐름(1회성 선점·전 세션 폐기·계정 열거 방지·링크 로그 미기록)은 모범 수준입니다.
- 이모지 금지 규칙, lucide 아이콘 규칙은 전 범위에서 위반 0건입니다.

**문제는 "설계는 맞는데 구현이 그 설계를 배신하는 지점"에 몰려 있습니다.** 발견된 치명 13건 중 10건이 같은 성격입니다 — 주석에 왜 그렇게 해야 하는지까지 적어 두고 정작 코드는 다르게 동작합니다.

**대조 근거**: 후원 오버레이는 같은 실수를 피했습니다 — 레이아웃 transform 은 바깥 래퍼(`overlay-client.tsx:645-649`), 애니메이션은 안쪽 `DonationCard`(`:706-708`)에 분리되어 있습니다. `RouletteBoard` 도 당첨 확정 시 애니메이션 클래스를 빼는 처리가 되어 있습니다. **게임 보드만 두 개를 한 요소에 겹쳐 놓았습니다.**

**조치**: 래퍼를 한 겹 나눕니다. 바깥에 transform(+`boardRef`), 안쪽에 애니메이션 클래스.

### C-2. 게임 중복 참여 차단이 클라이언트가 만든 값에만 의존한다 — 추첨 결과 조작 가능

`src/app/api/play/[code]/route.ts:74` · `src/server/services/games.ts:528` · `prisma/schema.prisma:1715`

```ts
const entryKey = input.donorId ? `donor:${input.donorId}` : `dev:${sha256(input.deviceKey)}`;
```

`deviceKey` 는 요청 본문의 `clientId` 를 그대로 받은 값이고, 서버 검증은 `/^[a-zA-Z0-9_-]{8,64}$/` 형식뿐입니다. `games.ts:489` 의 주석은 "IP + UA 해시"라고 적혀 있지만 **실제로는 브라우저가 만들어 localStorage 에 보관하는 값**입니다.

**재현**:
```bash
for i in $(seq 1 30); do
  curl -sX POST https://.../api/play/ABC123 -H 'Content-Type: application/json' \
    -d "{\"clientId\":\"aaaaaaaa$i\",\"name\":\"내계정$i\",\"entry\":\"\"}"
done
```
순위 추첨에 표 30장이 들어갑니다. 다른 시청자가 10명이면 당첨 확률 75%. 콘솔에서 `localStorage.removeItem('donaido_play_id')` 한 줄, 또는 시크릿 창을 열기만 해도 재참여됩니다. 추가로 `play-client.tsx:33` 은 저장이 막힌 브라우저에서 **호출할 때마다 새 값**(`tmp${Math.random()}${Date.now()}`)을 만들어, 사생활 보호 모드 사용자는 새로고침만으로 반복 투표가 됩니다.

보상이 걸린 실시간 추첨이라 조작 시비의 핵심입니다. 문서가 내세운 "회차 단위 유니크 제약으로 중복 참여 차단"이 실질적으로 성립하지 않습니다.

**조치**: `entryKey` 를 서버가 아는 값으로 만듭니다 — 최소 `sha256(clientIp + userAgent + roundId)` 를 clientId 와 함께 섞고(둘 중 하나만 같아도 차단), 회차별 IP+UA 상한(예: 3건)을 별도로 겁니다. 보상이 큰 회차는 로그인 필수 옵션이 근본 해법입니다.

### C-5. `reserveYouTubeQuota()` 가 원자적이지 않다 — 할당량 상한 무력화

`src/server/services/broadcast-dispatch.ts:37-43`

```ts

if (used + cost > env.youtube.dailyQuota) return false;
await kv.set(key, String(used + cost), 60 * 60 * 30);
```

GET → 계산 → SET 사이에 원자성이 없습니다. **같은 프로젝트의 `kv` 에는 이미 Lua 로 원자화된 `incr` 가 있습니다**(`src/server/redis.ts:73-82, 126-133`) — 쓰지 않고 있습니다.

**재현**: 후원 10건이 동시 도착 → 10개 요청이 모두 `used=0` 을 읽고 각각 50을 기록 → 카운터는 50만 증가, 실제 소비는 500 units. ECS 다중 인스턴스면 더 커집니다. 결과적으로 하루 상한이 무력화되고 구글 쪽 실제 할당량이 먼저 소진되어 403 이 옵니다.

**연쇄 문제 3건이 같은 함수에 있습니다.**
- **선점 롤백 없음**(`:359`): 50 units 를 선점한 뒤 전송이 실패해도 반환하지 않습니다. 유튜브가 5분간 5xx 를 내면 실제 소비 0인데 카운터만 2,000 units 가 사라집니다.
- **KST 리셋**(`:38`): `kstDateKey()` 를 쓰지만 **YouTube Data API 할당량은 태평양시(PT) 자정에 리셋**됩니다. PT 하루 안에 우리 카운터는 한 번 더 리셋되어 최대 2배를 허용하고, 실제로는 10,000 에서 구글이 403 을 던집니다.
- **전역 단일 카운터**(`:38`): 채널별 상한이 없습니다. 게임 참여 링크 공유(`api/studio/games/share`)에는 **rate limit 이 전혀 걸려 있지 않아**, 크리에이터 1명이 버튼을 200번 누르면 전체 서비스의 후원 채팅이 그 날 마비됩니다. 결제는 정상 완료되므로 후원자는 돈을 내고 채팅에 안 나오는 상황을 겪습니다.

### C-7. 승인 성공 트랜잭션이 조건부 갱신이 아니다 — 정산 원장 3분개 중복 가능

`src/server/services/donation-flow.ts:1103-1148`

```ts
await tx.paymentTransaction.update({
  where: { id: txn.id },            // status 조건이 없다
  data: { status: 'APPROVED', ... },
});
```

4번째 방어선인 `payment_transaction_approved_uniq` 는 "같은 donation 에 APPROVED **행** 2개"를 막는데, 여기서는 **행 1개를 두 번 UPDATE** 하므로 인덱스가 발동하지 않습니다. 뒤이은 `donorCreatorLink.upsert` 의 `increment` 와 `postDonationSettlement` 도 함께 두 번 돕니다.

`postDonationSettlement`(`settlement.ts:289-293`)는 `DONATION_GROSS` 존재 여부를 읽어 막지만 read-then-write 이고, **`settlement_ledger` 에 `(donation_id, entry_type)` 유니크가 없습니다**(스키마·마이그레이션 모두 일반 인덱스뿐). READ COMMITTED 에서 두 트랜잭션이 겹치면 둘 다 "없음"을 읽고 각각 3분개를 넣습니다. **원장은 append-only 라 되돌릴 수 없습니다.**

**실제로 검증되고 있는 것** (23개 파일 / 4,045줄): MO 재전송 중복 차단, 속도·일일 한도, 타임아웃 후 `inquire` 확정, UNKNOWN 미확정 유지, **원장 append-only 트리거 실동작**, PIN 콜백 중복·동시 2건·만료, 확인 링크 1회 소비, 웹 PIN 멱등키·쿠키 격리, 금칙어 ReDoS 선형시간, 로그 마스킹, 수수료·부가세·원천징수, 집계 예약/롤백, 수동 대사 동시성, 추첨 21건. 상당히 촘촘합니다.

**문서가 약속한 보증 중 테스트가 없는 것**

1. **웹훅 인증 자체** — `tests/setup.ts:15` 가 `MO_ALLOWED_IPS=''` 로 비워 두어 **IP 허용목록 코드 경로가 한 번도 실행되지 않습니다.** PIN 콜백의 `X-Pin-Secret` 검증·401 응답·`webhook_log` 기록도 테스트 없음
2. **SAFE_MODE 대체 경로(C-8)** — `setup.ts` 가 `SAFE_MODE=true` + `PAYMENT_PROVIDER=mock` 이라 `safeMode && provider !== 'mock'` 분기가 **한 번도 실행되지 않음**. 운영에서 가장 위험한 분기가 무검증
3. **`src/lib/crypto.ts` 전체** — encrypt/decrypt 왕복, authTag 변조, `masterKey()` 길이 분기 전부 0건
4. **인증·세션 전반** — 로그인 성공/실패/레이트리밋, 세션 만료·revoke, `requireCreator` 상태별 분기, 비밀번호 재설정 1회성 (CSRF 동일 출처만 있음)
5. **`payment_transaction_approved_uniq` 실동작** — 4번째 방어선이 DB 에 있다는 것만 SQL 로 확인될 뿐 테스트가 붙잡고 있지 않아 **H-32 의 DROP 사고를 CI 가 잡지 못함**
6. **`executePayment` 동시 2회 진입(C-7)과 원장 3분개 중복** — 없음
7. **멱등키 `IN_PROGRESS` 고착(C-13), MO `PENDING` 복구** — 없음
8. **`assertProductionSafety` / `assertBootSafety`** — 없음. 운영 설정 회귀를 잡을 수단이 전혀 없음
9. **유튜브 전 영역** — OAuth 콜백, 토큰 갱신 실패, 할당량 경쟁, `formatChatMessage` 포맷 테스트가 하나도 없음
10. **KEYWORD 정규화(H-1)** — 테스트가 키워드를 `'도네이도'`(공백 없음)로 넣어 **버그를 그대로 지나칩니다.** 이 한 글자만 바꿨어도 잡혔을 건입니다
