## 2. 검증 방법 — 무엇을 어떻게 돌렸는가

수정만 하고 "될 겁니다"라고 말하지 않기 위해, 네 단계를 실제로 실행했습니다.

### 2-1. 빈 DB 에서 마이그레이션 재적용

`CLAUDE.md` 의 규칙("스키마를 바꾼 뒤에는 반드시 빈 DB 에서 처음부터 적용되는지 확인")대로,
임시 PGlite 인스턴스에 35개 마이그레이션을 처음부터 적용했습니다.

**여기서 실제 오류가 나왔습니다.**

```
Migration name: 20260902160000_audit_fixes_2
Database error code: 42P17
ERROR: functions in index predicate must be marked IMMUTABLE
```

부분 유니크 인덱스 조건식에 `"entry_type"::text IN (...)` 를 썼는데,
PostgreSQL 은 **enum → text 캐스트를 STABLE 로 분류**하므로 인덱스 조건식에 쓸 수 없습니다.
개발 DB 처럼 이미 컬럼이 있는 환경에서는 조용히 넘어가고, **신규 배포에서만 터졌을** 오류입니다.
enum 리터럴로 직접 비교하도록 고쳤습니다.

```sql
AND "entry_type" IN (
  'DONATION_GROSS'::"ledger_entry_type",
  'PG_FEE'::"ledger_entry_type",
  'PLATFORM_FEE'::"ledger_entry_type"
)
```

이 검증을 건너뛰었다면 배포 당일 마이그레이션이 중단됐을 것입니다.

### 2-2. 전체 테스트

`npm test`(격리된 PGlite, 개발 DB 를 건드리지 않음)로 23개 파일 257건을 돌렸습니다.
**최초 실행에서 22건이 실패했고, 그중 대부분이 제 수정이 만든 회귀였습니다.** (3-1 참조)

### 2-3. 프로덕션 빌드

`next build` 는 일부 공개 페이지를 프리렌더하면서 DB 를 읽으므로, 임시 DB 를 띄운 상태로 돌려
전 라우트가 빌드되는 것까지 확인했습니다.

### 2-4. 회귀 테스트 신규 작성

이번 수정분이 나중에 조용히 되돌아가지 않도록 테스트 2개 파일을 새로 썼습니다.

- `tests/db-guards.test.ts` (94줄) — 부분 유니크 인덱스와 원장 append-only 트리거가 **DB 에 실제로 존재하는지** 검사.
  이 제약들은 Prisma 스키마로 표현할 수 없어 raw SQL 로만 존재하는데, Prisma 는 "스키마에 없고 DB 에 있는" 인덱스를
  **삭제하는 마이그레이션을 자동 생성**합니다. 누가 스키마를 한 번 고치고 `migrate dev` 를 돌리면 중복 결제 4중 방어의
  마지막 겹이 조용히 사라집니다. 그 사고는 사람 눈으로 못 잡습니다.
- `tests/audit-fixes-3.test.ts` (278줄) — 이번에 고친 항목의 "고치기 전이었다면 실패했을" 조건 20건.

## 3. 검증에서 발견해 추가로 고친 것 — 수정이 만든 회귀

이 절이 이 보고서에서 가장 중요합니다. **수정 작업 자체가 새 버그를 만들었고, 검증이 그것을 잡았습니다.**

### 3-1. 요청 컨텍스트 밖에서 `headers()` 호출 (테스트 22건 중 14건의 원인)

IP 기준 속도 제한을 여러 입구에 추가하면서 `consumeIpRateLimit` 을 서비스 함수 안쪽에 넣었습니다.
그런데 `headers()` 는 **요청 컨텍스트 안에서만** 쓸 수 있습니다. 크론·워커·테스트가 같은 함수를 부르면
거기서 예외가 터지고, 정작 하려던 일(후원 처리)이 통째로 실패합니다.

IP 는 속도 제한의 **보조 정보**이지 작업의 전제가 아닙니다. 얻지 못하면 `null` 로 돌려주고
판정은 호출부의 `failClosed` 정책에 맡기도록 고쳤습니다.

```ts
export async function clientIpFromHeaders(): Promise<string | null> {
  try {
    const h = await headers();
    return clientIpFrom((name) => h.get(name));
  } catch {
    return null;   // 요청이 없는 곳에서는 작업을 깨뜨리지 않는다
  }
}
```

### 3-2. 최소 정산 요청 금액 기본값 (테스트 6건의 원인)

이체 1건당 은행 수수료와 확인 공수가 고정으로 드는데 하한이 없어서, 100원짜리 요청도 같은 비용이 나갔습니다.
기능은 넣되 **기본값을 10,000원으로 두었더니 기존 동작이 바뀌어** 정산 테스트가 깨졌습니다.

하한은 코드가 정할 문제가 아니라 **사업 정책**입니다. 기본값을 `0`(하한 없음)으로 되돌리고,
운영에서 정한 값을 `SETTLEMENT_MIN_REQUEST_AMOUNT` 로 켜도록 했습니다. 기존 동작은 그대로입니다.

### 3-3. 유튜브 할당량 소진 사유가 "조회 실패"로 뭉개짐

방송 조회(`liveBroadcasts.list`)도 할당량을 쓰도록 계상을 추가한 결과,
할당량이 소진되면 **채팅 전송보다 조회가 먼저** 걸리면서 사유가 `BROADCAST_LOOKUP_FAILED` 로 기록됐습니다.

할당량 소진은 "조회가 깨졌다"와 성격이 다릅니다. 태평양시 자정이면 저절로 풀리는 일시적 상태이고,
운영자가 봐야 할 조치도 다릅니다. `QUOTA_EXCEEDED` 를 별도 사유로 올리도록 고쳤습니다.

### 3-4. 할당량 카운터 날짜 기준이 테스트와 어긋남

유튜브 일일 할당량은 **태평양시 자정** 초기화가 구글 규격입니다(기존 코드는 KST 기준 —
하루 중 16~17시간 동안 카운터와 실제 잔량이 어긋납니다). PT 기준으로 고쳤는데,
기존 테스트가 KST 키로 카운터를 미리 채우고 있어 시나리오가 성립하지 않았습니다. 테스트를 새 기준에 맞췄습니다.

## 4. 이번 회차(4~9차 패치)에 추가로 고친 항목

앞선 1~3차 패치 내용은 선행 보고서를 참고하시고, 여기서는 이번에 새로 처리한 것만 적습니다.

### 4-1. 정산 원천징수 미리보기가 실제 기록과 어긋남 (높음)

**증상.** 정산 요청 화면은 원천징수·실지급 예상을 **정산 가능금 전액 기준**으로 한 번 계산해 고정 표시했습니다.
그런데 요청 금액은 크리에이터가 직접 입력합니다.

가능금 100만원 중 3만원만 요청하면 —

| | 화면 표시(수정 전) | 실제 기록 |
|---|---|---|
| 원천징수 | 33,000원 | **0원** (소액부징수) |
| 실지급 | 967,000원 | **30,000원** |

숫자가 통째로 다릅니다. 정산은 돈이 오가는 화면이고, 여기서 어긋나면 문의가 아니라 분쟁이 됩니다.

**수정.** 계산 규칙을 `src/lib/withholding.ts` 한 곳으로 옮기고(기존 `settlement.ts` 는 re-export 로 경로 유지),
입력 금액에 맞춰 그 자리에서 다시 계산하는 클라이언트 컴포넌트를 만들었습니다.
**서버 확정 로직과 같은 함수**를 쓰므로 규칙이 두 벌로 갈라질 수 없습니다.
가능금 초과·최소금 미달도 입력 중에 바로 알려 줍니다.

### 4-2. 관리자 자격을 완전히 회수할 수 없음 (높음)

**증상.** 관리자 화면에는 권한 "변경"만 있었습니다. 퇴사자를 처리할 수 있는 가장 낮은 단계가 `READ_ONLY` 인데,
**READ_ONLY 도 후원자 연락처·결제 이력·정산 내역을 전부 열람합니다.** 조직을 떠난 사람의 계정이 콘솔에 계속 들어옵니다.

**수정.** `revokeAdmin` 액션과 `admin_profile.revoked_at` 컬럼을 추가했습니다.

- 프로필 행은 **지우지 않습니다.** `admin_audit_log.admin_id` 가 이 행을 참조하므로,
  지우면 "누가 무엇을 했는지" 기록이 함께 끊깁니다. 자격은 거두되 기록은 남깁니다.
- 실제 차단은 `user.role` 을 일반 회원으로 되돌려서 합니다(`requireAdmin` 이 role 을 봅니다).
- 열려 있는 세션도 함께 만료시킵니다. 그러지 않으면 브라우저를 켜 둔 사람은 그대로 들어옵니다.
- 본인 회수·마지막 SUPER_ADMIN 회수는 막습니다(스스로 잠기는 사고 방지).
- 회수했던 계정을 다시 등록하면 새 행을 만들지 않고 기존 행을 되살립니다(`ADMIN_REINSTATE` 로 감사기록).

### 4-3. MT 문자 본문을 저장 전에 확인할 방법이 없음 (보통)

**증상.** 이 화면에서 저장한 문구가 **그대로 후원자 휴대폰에 찍히는데**, 글자 수 상한만 알려 줬습니다.

- 문자는 글자 수가 아니라 **바이트**로 SMS/LMS 가 갈립니다. 한글 한 자가 2바이트라
  "90자 이내" 감각으로 쓰면 장문으로 넘어가 **건당 요금이 3~4배**가 됩니다.
- 치환자를 `{금액}` 이 아니라 `{amount}` 나 `[금액]` 으로 잘못 쓰면 치환되지 않고 **그 글자가 그대로 발송**됩니다.

**수정.** 편집기를 클라이언트 컴포넌트로 바꿔 —
치환 후 실제 바이트 수와 SMS/LMS 판정, 예시 값이 들어간 발송 미리보기(발신 표기 포함),
모르는 치환자·대괄호 오용 경고를 실시간으로 보여 주고, 저장 시 확인창을 띄웁니다.

### 4-4. 관리자 목록 화면 13곳의 페이지 번호 처리 (보통)

**증상.** 5페이지를 보다가 필터를 걸면 결과가 1페이지로 줄어드는데 URL 의 `page=5` 는 남습니다.
조건에 맞는 건이 분명히 있는데 "조건에 맞는 항목이 없습니다"가 뜹니다.
관리자는 필터가 잘못된 줄 알고 조건을 지우고 처음부터 다시 찾습니다.

**수정.** `clampPageOrRedirect` 헬퍼를 만들어 13개 목록 화면에 적용했습니다(결과가 0건이면 진짜 빈 화면이므로 그대로 둡니다).
아울러 **정렬 보조키(`id`)를 9개 화면에 추가**했습니다 — 같은 시각 행이 여러 개면
페이지를 넘길 때마다 순서가 바뀌어 어떤 건은 두 번 보이고 어떤 건은 아예 안 보였습니다.

### 4-6. 재대조 후 추가로 고친 4건 (9차 패치)

높음 41건을 코드와 하나씩 다시 대조해 미완으로 확인된 것 중, 코드로 끝낼 수 있는 4건을 처리했습니다.

**H-41 — 해지한 후원자의 빌키가 결제사에 살아 있음.** 이 중 가장 무겁습니다.
자동출금 동의를 해지하면 내부 상태만 `REVOKED` 로 바뀌고, 결제사 해지 호출이 실패해도 로그만 남았습니다.
후원자는 해지했다고 알고 있는데 **출금 수단은 그대로 남아 있는** 상태이고, 그런 건을 찾을 방법조차 없었습니다.

- `payment_method_token` 에 `revoke_failed_at` / `revoke_attempts` / `revoke_last_error` 추가
- 실패 시 빌키 암호문을 **남깁니다** — 지우면 다시 시도할 방법이 사라집니다
- 성공 시 암호문을 **지웁니다** — 해지된 빌키를 보관할 이유가 없고, 남기면 유출 시 그대로 위험입니다
- 크론에 30분 간격 재시도(최대 12회) 추가. 상한을 넘기면 최고관리자에게 알립니다 — 계약·키 문제는 사람이 봐야 풀립니다

**H-40 — 고객지원 권한으로 서비스를 끊을 수 있음.**
크리에이터 승인·정지, 후원 코드 재발급, MO 번호 배정·회수에 권한 등급 가드가 아예 없었습니다.
고객지원의 일은 문의 응대와 조회이지 서비스 공급 중단이 아닙니다. `assertOperationAdmin`(SUPER_ADMIN·OPERATION)을 네 곳에 적용했습니다.

**H-27 — 정산 요약이 이름순 상위 30명만 계산.**
정산할 돈이 있는지와 이름 순서는 아무 관계가 없어서, 이름이 뒤쪽인 크리에이터는 잔액이 아무리 많아도 표에 나타나지 않았고 경고도 없었습니다.
**원장 금액 순 상위 50명**을 잡도록 바꾸고, 넘칠 때는 화면에 그 사실을 알립니다.

**H-21 — MO 번호 화면이 `<option>` 수만 개를 렌더.**
배정 `<select>` 를 행마다 그려서 200행 × 300명이면 6만 개가 됐습니다.
`<datalist>` 를 화면에 한 번만 두고 각 행이 참조하는 방식(`DatalistActionForm`)으로 바꿔, 선택지 DOM 이 목록 크기와 무관하게 한 벌이 됩니다. 이름 검색도 됩니다.

**문구·접근성 정리** — enum 원문 노출 3곳에 한글 라벨 적용(`userStatusLabel`·`adminPermissionLabel` 을 `lib/labels.ts` 로 통합),
액션 결과 메시지에 `role="status"`/`aria-live`, 표 안 `<select>` 5곳에 `aria-label` 추가.

1. **개발 DB 에 마이그레이션 적용** — 신규 3개가 아직 적용되지 않았습니다.
